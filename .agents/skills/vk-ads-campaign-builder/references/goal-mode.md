# VK Goal Mode And Write Safety

## Write Safety

- Read current campaign/group/banner first.
- Show plan, budget impact, and fields to change.
- Wait for explicit confirmation.
- Use `call_write_tool`.
- Reread state and report before/after.
- For agency/team Пространства include exact `workspace_project_id`.
- For a new campaign, call `vk_prepare_campaign`, then pass exactly one bootstrap ad group to `vk_create_campaign`. Do not include nested `banners`.
- Always read `checked_packages.goal_mode`, `goal_catalog`, `goal_source_verified`, and `goal_source_evidence` before using `priced_goal`: `required` needs a named goal proven unique in that package's `goal_catalog`, `forbidden` rejects it, and `unsupported` stops before POST.
- Match the catalog, not the group. `priced_event_type=7` and `priced_event_type=30` both read `goals.json`, which returns the `topmailru` and `mobile_install` groups in one response; VK accepts a Top@Mail.ru counter goal for `objective=site_conversions` even at event 30. `expected_goal_source` is the documented VK label for the event, not a requirement on the group. `priced_event_type=43` reads `remarketing/inapp_events.json` and accepts only `tracker.id + event.name` from `vk_get_inapp_events`. Catalogs are not interchangeable: a `goals.json` goal is incompatible with a VK Mini Apps package and vice versa. Missing, incomplete, duplicate, or ambiguous catalog evidence is fail-closed.
- Before adding a group to an existing campaign, read the parent with `vk_get_campaign`. VK can represent an existing `objective=vk_miniapps` event as a provider-managed `priced_goal` with `source_id=0`, empty `name`, and non-empty `miniapp_inapp_event_name`. The inheritance contract is not live-verified: omit group-level `priced_goal`, do not replace the event with a guessed tracker, and stop when `vk_create_ad_group` returns `miniapp_goal_inheritance_unverified` without POST. Never copy or synthesize `source_id=0` into a write payload.
- Do not require a goal merely because the objective is `site_conversions`, and do not treat `options.settings.priced_goal`, the package name, or package 3509 (`priced_event_type=0`) as proof of goal compatibility.
- Do not remove an incompatible goal without user agreement. Offer the explicit alternatives: keep CPC/CPM without a named goal, or choose a compatible goal/oCPM package.
- Treat `package_priced_goal_forbidden`, `package_priced_goal_required`, `package_goal_source_mismatch`, `package_goal_source_unverified`, `provider_package_rejected_recently`, `package_rejection_registry_unavailable`, `miniapp_goal_inheritance_unverified`, and `package_goal_policy_unsupported` as no-side-effect preflight failures. Treat `provider_goal_package_mismatch` / `inconsistent_priced_goal` as a ban on retrying the same payload.
- Read `create_evidence` before choosing a package. It is a separate axis from catalogue access: `accepted_by_provider` means VK already accepted this package at create; `never_accepted_by_provider` means VK lists it as allowed but has never accepted it at create for any owner. Prefer `accepted_by_provider`. Never iterate over `never_accepted_by_provider` packages — `package_request=allowed` does not override that; pick another package or ask VK Ads support for access to one. `vk_prepare_campaign` repeats those packages in `provider_evidence_warnings`; show the warning to the user before asking for confirmation.
- Distinguish package failures by stage. `package_unavailable` from preflight happened before POST, so reread `vk_get_packages(objective, available_only=true)`. That listing excludes packages with an active confirmed `invalid_package` in the exact provider scope and reports their package/operation IDs separately; `vk_get_package(id)` remains diagnostic but marks the package unavailable for create. Registry read failure stops create.
- `provider_package_rejected` with provider code `invalid_package` means the VK catalog contradicted create: `retry_safe=false`; never retry the same package/payload. A different package is allowed only after fresh `available_only` and `vk_prepare_campaign` checks prove the expected goal source. Show the changed package ID, optimization, budget, region, and goal, then obtain a new ordinary text confirmation. If no compatible package remains, perform no POST and report the provider blocker.
- For that confirmed catalog/create contradiction, call `support_prepare_report` with the `operation_id`, show the sanitized draft, and call `support_send_message` only after explicit user consent.
- Treat the created campaign and bootstrap group as `blocked`. A successful campaign create must return both reread objects as `blocked`. Create remaining groups and banners with separate write tools, reread every object, and activate only as a final separate action.
- If the result contains `outcome=unknown` or `outcome=ambiguous`, call top-level `get_write_operation_status({ operation_id })`. Keep the same campaign name and never send another create.
- If status remains unresolved, offer a safe support draft containing the `operation_id`, never the raw payload or credentials.
